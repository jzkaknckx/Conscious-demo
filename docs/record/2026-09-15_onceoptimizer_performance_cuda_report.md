### 内存不是这次现象的首要解释

本次采样 RSS 峰值为 **1,480.01 MiB（约 1.45 GiB）**，相对基线增量为 **217.54 MiB**；系统可用内存最低仍有 **18,645.29 MiB**。没有 OOM 记录，中断类型是 `KeyboardInterrupt`。已有数据不支持“内存耗尽导致交换抖动”为首要原因；本次没有采集缺页率／I/O／CPU 占用，不能完全排除其它系统干扰。旧模型明确运行于 CPU，GPU 显存没有承担训练张量。

## 3. 可疑慢路径及改进优先级

### P0：区域与已有模板的全量局部匹配

`learn` 对每个新区域调用 `_region_match`。后者遍历**全部已有同模态区域模板**：先验证稀疏查询给出的中心，如果没有达到学习阈值，就把这个新区域的**每个像素**作为候选中心继续验证。

`SpatialStructureMatcher.evaluate` 对每个模板槽位、每批候选中心执行位置采样和邻域最大值计算，随后逐中心、逐槽位在 Python 中构造赋值、位图、组投票、几何约束与冲突判断。默认几何半径 2，对应每个预测位置 25 个偏移。

令新区域像素数为 P_r、同模态已有模板数为 T_r、平均槽位数为 K，密集验证的工作量近似为：

`Σ_r P_r × T_r × K × (2 × radius + 1)²`

另外还有 Python 对象构造与全图响应计算开销。这解释了空记忆时很快、已有模板增多后显著变慢的趋势，但需要新增分阶段计时确认具体占比。

建议：

1. **先复用稀疏检索与倒排关联生成的模板候选**，再做几何验证。形状、尺度范围、模态、描述子覆盖的可证明上界可用于提前剔除必不达阈值的模板。
2. 对真正需要补查的候选分块检验，优先高分位置；只保留最佳匹配和歧义竞争者所需数据，避免为大量失败中心创建完整 `StructureMatch/assignments` 对象。
3. 将评分、覆盖率和可向量化的几何约束放在 Tensor 批处理中；仅对保留中心执行 Python 角色与冲突检查。
4. **不能直接删除密集补查并把稀疏未命中当作新物体**。预算截断仍应标为“未充分检验”，否则会改变已有算法的保守学习语义并进一步制造新节点。需要给歧义分差检查保留足够竞争候选。

### P0：区域局部缓存重复生成整图响应

`_region_match` 为每个输入区域新建 `FeatureResponseCache`；该缓存重新处理整图有效性、门控，并用默认仅 32 项的 LRU 缓存保存描述子响应。同一图片在多个区域之间不能共享缓存，缓存淘汰也可能引发重复计算。

建议将**不依赖区域掩码的原始相似度／门控响应**在一次观察内共享，再在验证阶段叠加各区域的可评估掩码。按显存预算分块计算或仅计算真正使用的位置，记录命中率与 `map_computations`。不能直接把当前带区域掩码的响应缓存拿来跨区域复用，否则会改变未知／负证据含义。

### P1：II 层关系的全表查找

`_relations_and_proposals` 先枚举新区域对。对符合接触或半径条件的每一对，执行一次对 `gii.region_relations` 的全表扫描，寻找相同 `(source, target)` 的关系；新建关系时还再次用 `max(...)` 遍历已有键。

当新图区域数为 R、已有关系数为 E 时，最坏可出现 `O(R² × E)` 级关系查找。第 8 图已累积 34,982 条关系，不能因为实体提案预算只有 64 就认为这部分也被限制为 64 次：该预算是在关系构造之后才生效。

建议维护 `(source_id, target_id) -> 关系变体列表` 索引及单调关系 ID 分配器，将查找范围缩小到同一节点对；需要在区域归并时同步维护索引。区域对可按锚点空间网格枚举半径邻居，再并入实际接触对，避免遗漏远距离但有接触证据的关系。以上优化可以保持关系定义和判断标准。

### P1：全池复制、全量归并与索引重建

每次学习深复制 I／II／III 三个池；随后又复制 III 层实体快照。描述子签名、区域视图及等价归并也会遍历已有池。每次查询重新建立 `HypergraphIndex`，没有持久版本缓存。

建议按变更节点／边进行事务写集合或 copy-on-write，并保留提交原子性；将签名、区域视图、倒排索引按节点版本缓存，归并仅处理新增或改变的对象。不要以原地修改替代事务而失去异常时的一致性。优先先测量 `pool_deepcopy/entity_snapshot/region_update_and_merge` 再决定实现次序。

### P1：GPU 迁移仍保留大量主机往返

现有代码可把 CNN、相似度、门控和 `grid_sample` 张量运算放到 GPU，但区域分割、图字典、关系更新和逐中心赋值仍依赖 NumPy／Python。`SpatialStructureMatcher` 每槽位把有效掩码、最佳偏移与分数 `.cpu().numpy()`；描述子签名和 `.item()` 也可能引起设备同步。

`HypergraphIndex.feature_events` 对每个精确描述子类别先遍历所有超过阈值的采样点，逐个提取 Python 标量并排序，之后才截断到 64 个事件。在 GPU 上逐点 `float/int` 会产生大量细粒度同步。候选预算 128 只约束后续验证，不能约束之前的全部类别扫描。

建议把阈值过滤、确定性排序／top-k 和坐标解码保留在设备上，批量传回已筛选事件；保持相同分数下的坐标排序规则。描述子按模态堆叠批量比较，静态掩码／签名留一份 CPU 元数据，减少逐槽位同步。GPU 加速比目前不能预先保证，更不能期待 Python 图循环自动搬到 GPU。

### P2：实体复用与候选增长需要同时审查

8 张不同图片每次主学习均新建 64 个实体，`updated_entities=0`；最终候选数达到 512，稳定实体为 0。首次同 episode 重复后实体数也从 64 增至 95。这些现象**不是证据去重条目超额的证明**：该次账目检查 `invalid_evidence_records=0`，新增候选具有独立节点账目。

但它提示需要检查提案枚举与去重的稳定性，以及 `_align_entity` 所要求的 GmemII 精确编号对应能否在跨图区域匹配后重现。不同图片也可能没有共享物体，当前只有 8 张图片且没有语义真值，不能据此断言 III 层不可学习。

建议分别验证：同图重复下提案的规范表示是否稳定；跨图片复用的 GmemII 是否覆盖相同角色；实体拒绝由覆盖、位置误差还是歧义分差触发。然后再考虑更合理的提案排序／等价合并。单纯放宽阈值可能损害可靠性，不属于本次修改。

### P2：Notebook 额外检查与可观测性

最早 8 张图各自带一次初学查询；第 1 张另有一次重复学习。它们是可靠性测试的成本，但第 2–8 步未落在 `learn_view` 内的时间总计仅约 2.62%，关闭所有绘图不可能解释性地解决数分钟学习问题。

之前每 10 张才显示进度，8 张未完成时用户长期只看到第一步；第 9 张中断也没有开始时间记录。本次已修正：每张显示、30 秒心跳、进入学习前写日志，并分别记录编码、学习、初学查询、重复学习和其它开销。原来两线程配置只影响 PyTorch 主机算子，不让 Python 图循环并行；本次没有调整线程数或其它训练参数。

- Notebook 默认 `DEVICE=cuda:0`；初始化要求 CUDA 可用，真实执行一个 GPU 矩阵算子验证二进制兼容性，显示 Python 路径、torch 构建、设备名、计算能力和显存。无静默 CPU 回退。

## 6. 修复后的实际验证

除 cu126 架构问题外，实际 CNN 验证发现第二个环境冲突：进程继承的 `LD_LIBRARY_PATH` 重复包含
`/usr/local/cuda/lib64`，从中加载 cuDNN **9.0.0**，而当前 PyTorch 需要 **9.10.2**。
最初的 CNN 测试因此出现 `cudnnGetLibConfig` 符号加载失败；清除该测试进程的旧库路径后，GPU 学习通过。

已注册用户级内核 **consciousLinux (CUDA 12.8)**，内部名称 `conscious-linux-cu128`，
解释器仍是同一个 consciousLinux Python，内核启动环境优先使用该 Python 环境下 `torch/lib` 与 `nvidia/*/lib`。
这不会更改系统库、驱动或其它内核的环境变量。Notebook 元数据已指向新内核；VS Code 若沿用上次选项，需要手动选择这个名称。
单纯在已经启动的 Python 中修改 `os.environ` 不能可靠替换已加载的 cuDNN，因此要求重新启动内核。

- 环境升级完成：`torch 2.10.0+cu128`、`torchvision 0.25.0+cu128`；`pip check` 输出 `No broken requirements found`。
- 新 wheel 的架构列表包含 `sm_120`，设备识别为 RTX 5060 Ti，CUDA 构建版本为 12.8。
- GPU 矩阵算子、Retina CNN、`grid_sample`、32×32 合成图首次／同 episode 再次学习、层级查询均通过。
- 明确断言 GmemI 原型和掩码张量位于 CUDA；分阶段计时及密集搜索计数成功返回。
- Notebook 首单元增加实际矩阵和卷积预检，并提前调用 cuDNN 版本检查，防止旧库冲突拖到训练中才暴露。
- 验证详情：[实际 CUDA 检查](../../results/cuda_environment_20260915/after_cuda_check.json)、[Notebook 预检](../../results/cuda_environment_20260915/notebook_preflight.json)、[内核配置](../../results/cuda_environment_20260915/kernel/kernel.json)。
- 源码 `py_compile`、全部 Notebook 代码单元静态编译、`git diff --check` 通过。

32×32 合成图只用于验证设备兼容性与执行通路，不用于推算 256×256 ILSVRC 的训练速度或显存需求。

### 7.4 为什么 CPU、GPU、内存与显存看起来都不高

**CPU 总占用低，仍可能受单线程限制。** 本机当前可见 20 个逻辑 CPU。如果监视器按全部逻辑 CPU 归一化，一个线程满载约显示为总 CPU 的 5%；有些进程监视器则把同一情况显示为 100%，需要区分口径。CPython 3.11 的 Python 字典、对象构造和逐项循环通常不能依靠增加线程自动铺满全部核心。当前 `torch.set_num_threads(2)` 控制部分 CPU 张量算子，不负责并行化这些 Python 循环。这里未保存运行期间逐核 CPU 使用率，所以不能直接断言某个核当时已满载。

**GPU 低占用，可能是主机没有持续提供足够大的工作块。** 源码显示以下串行依赖链：

`Python 选模板／槽位 → 发射小 Tensor 算子 → 取回 GPU 结果 → Python 判断／构造对象 → 发射下一组算子`

- `FeatureResponseCache.evaluable()` 逐通道读取 GPU 掩码 `.item()`；匹配器先调用一次，`get()` 内又调用一次。静态可评估条件因此可能反复触发很小的数据读取及同步。
- `SpatialStructureMatcher.evaluate()` 逐槽位获取 `known`、最佳索引和分数的 `.cpu().numpy()`，接着逐中心、逐槽位执行 Python／NumPy 的赋值、组投票、几何与冲突判断。
- `HypergraphIndex.feature_events()` 在 GPU 阈值筛选后，仍逐坐标调用 `float/int` 并由 Python 排序，截断发生在此后。
- 当前索引和局部缓存经常重建；不少响应图在稍后又被重新计算。

这些依赖让 GPU 算完小块后等 Python，Python 取值时又等 GPU。两者的总体利用率都可能不高，而总耗时很长。**这是由代码与新日志支持的首要机制假设；尚无 CUDA 时间线，不能给出“等待、拷贝、Python 各占多少”的实测百分比。** 用户观察到的低 GPU 利用率与该机制一致，也应确认监视器显示的是 CUDA/compute 而非图形引擎。

**内存／显存占用衡量存放量，不等于吞吐或忙碌程度。** 本次运行记录：

- RSS 采样峰值 **2,335.82 MiB**，相对基线增加 **313.41 MiB**；系统可用内存最低 **17,811.73 MiB**。
- PyTorch 显存分配峰值 **50.10 MiB**，缓存保留峰值 **64 MiB**；结束时 GPU 可用约 **14,901.56 MiB**。这不是设备上所有进程的总显存占用。
- 第 1 步持久图中的 CUDA Tensor 存储仅约 **0.0416 MiB**；图的主要内容是 CPU 上的节点／边字典和元数据，不能把模型等同于一个拥有巨大权重矩阵的神经网络。

目前更像是**重复搜索与串行调度瓶颈**，不是容量不足。较小的 LRU 与逐小块处理也限制了常驻显存；显存没有用满，并不证明程序没有执行 GPU 计算。反之，主动塞满显存不会自动加速。

### 7.5 按本次证据重新排序的改进方向

1. **优先减少无意义模板密集验证。** 先按共享描述子、模态、空间范围与可证明的匹配上界筛选模板，再作几何验证。维护足够的竞争者以保留歧义判断；预算未检完仍应标为未知，不能用稀疏未命中直接判新节点。当前超过 99.9% 的模板比较进入回退，比调整 CNN 更值得投入。
2. **在一次观察内复用响应与静态可评估条件。** 缓存不依赖区域掩码的原始响应，再独立应用局部掩码；预先计算可评估布尔值、CPU 静态掩码与描述子签名，避免每槽位重复 `.item()`。采用有字节预算的共享缓存／批处理，利用部分空闲显存。256×256 float32 单张响应约 0.25 MiB，当前 32 张响应仅约 8 MiB；这一计算仅用于设计容量，不能直接把缓存无限放大，也不能共享已经混入不同区域掩码的结果。
3. **按描述子／模板／位姿批量处理，而不是逐项调用 GPU。** 将分数、覆盖率、可向量化的约束与候选筛选留在设备上，一批完成后再回传少量幸存候选。全局事件的筛选和稳定排序也应避免逐点 `.item()/float/int`。不能仅机械添加 `non_blocking=True`：Python 下一行若需要结果，依赖仍要求等待。
4. **避免为所有失败中心创建完整匹配对象。** 先使用紧凑 Tensor/数组保存分数和必要状态，保留最佳候选及歧义竞争者后再构造 `StructureMatch`。保留现有冲突拒绝、角色多重性和有效覆盖语义，并用小例子的旧实现对照。
5. **学习外的初学复查另列成本。** 第 2–6 图各花 31.87–58.54 秒，约占各整步 9%–16%；可作为独立评估阶段执行，或使用明确的固定探针协议降低频率。第 1 图重复学习为 168.80 秒，测试价值在证据去重，不能将其误当常规训练成本。本次保留原测试协议，仅指出可调整的评估成本。
6. **关系索引、copy-on-write 与实体复用列为后续优化。** 它们有必要，但当前关系生成约 0.60%、深复制约 0.13%，先做这两项无法产生数量级改善。III 层跨图更新仍为 0、稳定实体为 0，应继续检查提案／身份复用，但不能用放宽阈值掩盖性能问题。

### 7.6 下一步如何验证机制，而不是继续等待全量训练

建议单独进行一次**有界的性能采样实验**，本轮未执行：

- 在少量已学习记忆上，对固定真实图片采样一个区域匹配片段，记录 CPU 每线程时间与墙钟时间；区分单核忙碌和阻塞等待，避免只看全机 CPU 百分比。
- 用 CPU/CUDA profiler 或 CUDA 时间线查看 `.item()`、设备到主机拷贝、同步调用、小 kernel 的持续时间及间隔；同时确认 GPU compute 的利用率口径。不要对数分钟完整训练启用无限制调用栈和形状追踪，以免诊断本身耗尽内存。
- 同时记录缓存命中／淘汰、响应图计算次数、模板比较数、密集中心数与幸存中心数。以减少这些重复工作量和减少主机往返为验收指标，而不是以“显存填得更多”为目标。
- 对同一冻结记忆和同一输入分别测 CPU/GPU，保持预算、精度及候选顺序一致；先核对接受／拒绝与歧义输出，再比较墙钟速度。本次跨图训练已经有轻微状态分岔，不适合作为严格等价性判据。

综上，本次正式 GPU 日志将主要问题从“可能在多个图阶段”收敛到“**区域密集匹配与前置查询的重复工作，以及其间细粒度 CPU/GPU 往返**”。应以此更新优化顺序，无需继续把排查重点放在已修复的 CUDA 安装或增加硬件容量上。
