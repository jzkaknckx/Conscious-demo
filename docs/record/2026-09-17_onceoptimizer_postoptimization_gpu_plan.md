# 优化后运行复查与 GPU 计算／存储迁移评估

## 1. 结论

本次优化有效：同一训练顺序下，第 2–6 张图的主学习累计耗时由 1,984.15 秒降至 1,312.35 秒，约 **1.51 倍加速、减少 33.9% 时间**；其中学习前查询约快 **10–14 倍**。

但区域匹配仍随记忆增长显著变慢。新的主要证据是：**256 MiB 共享响应缓存发生大量淘汰与重算，候选筛选又位于响应生成和采样之后**。因此，小规模对照的收益不能直接外推到更大的长期记忆。

将更多计算和数据放入显存是可行的，建议优先顺序为：

1. 扩大／重排当前观察的响应工作集，消除缓存反复淘汰。
2. 将槽位采样、评分、必要条件筛选放到 GPU 批处理中，只回传幸存候选。
3. 提前使用可证明的上界剔除无效候选，减少而不只是加速穷举。
4. 按需建立 GPU 图索引与数值快照，暂时保留 CPU 的权威图对象、证据账目和事务提交。

“把全部 Python 图对象直接搬到显存”不能自动并行化现有算法，也不是当前收益最高的第一步。

本次仅复查日志、源码和报告，不修改代码、不调参、不重新运行训练。

## 4. 关键发现：共享缓存容量与访问顺序不匹配

### 4.1 缓存到达容量后收益明显衰减

每张 256×256 float32 响应图为 262,144 字节，即 **0.25 MiB**。当前父缓存预算 **256 MiB**，最多保存约 **1,024 张**这样的响应图；实际按描述子签名去重，不能直接把节点数当作唯一响应数。

| 图片 | 优化前局部响应计算 | 优化后计算／未命中 | 优化后父缓存淘汰 | 父缓存峰值 |
| --- | ---: | ---: | ---: | ---: |
| 2 | 165,552 | 1,324 | 300 | 256 MiB |
| 3 | 285,376 | 164,805 | 163,781 | 256 MiB |
| 4 | 434,586 | 419,206 | 418,182 | 256 MiB |
| 5 | 522,624 | 507,141 | 506,117 | 256 MiB |
| 6 | 590,976 | 574,979 | 573,955 | 256 MiB |
| 10 | 无对照 | 923,650 | 922,626 | 256 MiB |

第 2 张图重算次数减少约 **99.2%**；第 6 张只减少约 **2.7%**。这是实际运行中加速比例下降的重要解释。

源码使用“区域外循环 → 模板遍历 → 槽位响应访问”。一个区域扫过的描述子工作集超过缓存后，较早响应会被逐出；下一个区域按相近顺序遍历，又可能把即将需要的响应逐出。日志中未命中与淘汰数几乎仅相差 1,024，强烈支持这一缓存反复淘汰机制。尚未记录完整访问轨迹，不能进一步确定每个模态或具体模板的贡献比例。

注意，当前 `response_cache_hits` 混合累计父缓存和区域局部缓存命中，不能直接用它与父缓存 misses 计算严格的父缓存命中率。后续应拆开统计两层访问、唯一描述子数、工作集大小及重用距离。

### 4.2 必要条件筛选有效，但执行得偏晚

第 10 张：

- 区域—模板比较 88,832 次，其中密集回退 88,815 次，仍约 **99.98%**。
- 密集中心 16,291,553 个；槽位×中心累计 168,904,577。
- 前筛排除 16,116,110 个中心，175,478 个中心进入完整赋值；合计包含稀疏中心，排除比例约 **98.92%**。

这说明大量失败中心已经免于 Python 赋值／几何对象构造。但当前筛选发生在所有槽位响应获取、邻域采样，以及整批结果回传 CPU **之后**。因此，提前排除的候选此前仍支付了响应重算、采样、小算子调度及传输成本。

不能把“98.92% 被筛掉”理解为“98.92% 的完整计算已被省掉”。下一轮应尽量将筛选前移，并让筛选本身留在 GPU 上。

## 5. 更多数据放入显存，容量上是否可行？

### 5.1 当前记录支持进行有界的扩大实验

本次显存分配峰值约 **307.64 MiB**，PyTorch reserved 峰值 **322 MiB**；结束时设备剩余可用约 **14,642.31 MiB**。进程 RSS 峰值约 **2,339.48 MiB**，系统可用内存最低约 **23,497.61 MiB**。这些数据不支持“内存容量不足”为当前主因。

`cuda_allocated` 在每图结束时回落到约 31 MiB，是因为当前观察的工作缓存被释放；评估运行所需资源应看峰值，不能只看步末快照。剩余显存是当时的观测，后续其他程序可能改变它。

以“一节点最多一张 float32 全图响应”的保守、未去重估算：

| 规模 | 仅响应图的存储量 |
| --- | ---: |
| 1,024 个描述子 | 256 MiB |
| 第 10 图学习前 7,896 个 I 层节点 | 1,974 MiB，约 1.93 GiB |
| 第 10 图学习后 8,294 个 I 层节点 | 2,073.5 MiB，约 2.03 GiB |
| 100,000 个描述子，未来情景 | 25,000 MiB，约 24.41 GiB |

当前约 2 GiB 的响应工作集在现有显存余量下具备尝试空间，但不是整个算法的显存需求：还包括输入、门控、掩码、索引、局部缓存、采样中间量、复制与分配器开销。上述节点数来自长期池，不代表实际查询到的唯一描述子数；真实工作集应通过签名去重后统计。

**可以先验证受限的更大缓存，例如 2 GiB 级预算，或按所需描述子的精确字节数与预留显存动态决定预算。** 不应把剩余显存全部交给响应缓存，也不应无界预计算每个节点的响应。随着节点数增长，单纯扩大缓存迟早再次失效。

### 5.2 访问重排比长期依赖大缓存更可持续

可以将区域优先的循环改为模板块／描述子块优先：

1. 固定本次观察与提交前记忆，列出待检查的区域和模板。
2. 为一组模板加载它们共用的原始响应，处理需要该组响应的多个区域。
3. 每个区域分别累积最佳候选和歧义竞争者。
4. 处理完所有必要模板后，再按原规则决定更新、歧义或新建。

这样让已计算响应在被淘汰前真正得到复用，即便全工作集不能常驻，也可减少循环式重算。区域掩码仍必须独立施加，不能把区域 A 的已掩码响应直接给区域 B。

这一改造需要保留每个模板“稀疏候选达学习阈值则不再密集回退”的分支、最佳匹配的排序规则、逆向范围检查和竞争分差；仅改变遍历顺序，也要测试同分候选及歧义结果是否保持一致。

## 6. 计算搬到 GPU：可行方式与边界

### 6.1 先迁移密集数值链路

当前 CNN、响应相似度、门控、`grid_sample` 和邻域最大值已在 GPU；欠缺的是让它们形成连续批处理，而不是由 Python 逐槽位组织，再把每批全部结果交回 CPU。

建议把以下数据作为 GPU Tensor：

- 按模态组织的描述子与掩码矩阵。
- 区域模板的槽位节点索引、相对位置、权重、组索引和有效长度。
- 一批模板—区域—中心的任务索引与局部有效掩码。
- 采样分数、最佳偏移、有效权重、覆盖率和必要条件筛选结果。

连续在设备端执行：

`批量响应 → 批量槽位采样 → 加权分数／覆盖率 → 前筛 → 压缩幸存索引 → 少量候选回传`

初版可以继续让 CPU 对幸存候选执行原有角色冲突、几何核验与图写入。这保留了可靠的参考实现，避免一次重写整个优化器。在同分排序、重复角色、共享成员、缺失模态、掩码孔洞、非有限值和阈值附近必须做对照。

原标量验证使用 CPU 双精度累加，直接换 GPU float32 归约可能改变阈值边界。应先保持数值定义；使用不同归约顺序时，对临界结果保守留存并复核，不能用未经误差分析的激进阈值预筛。FP16/BF16 不是本次首先建议的优化。

### 6.2 批量化必须控制中间量

若候选中心块 B=2,048、槽位 K=64、邻域 D=25，仅 `[B,K,D]` float32 采样值就约 **12.5 MiB**；显式二维坐标再约 **25 MiB**。同时展开 32 个模板，仅这两项就约 **1.17 GiB**，还未包含响应与其它中间量。

因此不建议一次构造 `[所有模板, 所有位置, 所有槽位, 所有偏移]` 的巨型张量。需要按模板、中心、槽位分块，复用缓冲区，尽量用广播或融合实现避免物化重复坐标，并以实际峰值约束块大小。

GPU 利用率低并不是“批越大越好”的充分依据。真正的验收指标是墙钟时间、重复工作量、同步次数与结果一致性。

### 6.3 图存储可以使用 GPU 数值快照，保留 CPU 权威状态

Gmem 的逻辑超图结构可以保留，物理表示不必继续完全由逐节点 Python 对象承担计算：

| 数据 | 建议位置与形式 | 理由 |
| --- | --- | --- |
| 图 ID、类型、episode 来源、证据账目、事务提交 | 先保留 CPU | 动态字典与不规则写操作较多，当前耗时占比小 |
| I 层描述子、掩码、可评估元数据 | GPU 分模态矩阵，必要时保留 CPU 静态副本 | 避免大量小 Tensor 和逐节点调用 |
| II 层槽位、相对坐标、组权重 | GPU 平坦数组与 offsets／CSR 索引 | 支持多个模板批量 gather 与采样 |
| III 层成员关系与展开叶槽位 | 有版本的 GPU 索引快照，按需更新 | 保留重复角色、多归属及虚拟挂载语义 |
| 本次图片的原始响应、门控、有效域 | GPU，有界且可复用 | 当前最直接的重算来源 |
| 匹配分数与候选标记 | GPU，压缩后只回传幸存项 | 避免传回约 99% 最终失败的候选结果 |

CSR/offsets 应以“角色／槽位”为条目，不能将同一低层节点的多个角色折叠成唯一邻居，否则会破坏多重性。镜像索引在一次学习过程中只读；提交后依据节点／区域／实体版本失效或增量更新。响应缓存还必须绑定输入观察与掩码语义，不能因为模板不变就跨图片复用图像响应。

**把 Python dict 的每个数值分别改为 CUDA 标量，再照旧用 Python 循环访问，可能增加 `.item()` 和同步开销。** 显存迁移的关键是批量的数据布局与算子边界，而不只是数据的 device 标签。

## 7. 下一轮建议的优先级与验收方法

### 第一优先：验证缓存重算是否可大幅消除

在相同冻结记忆与同一张真实输入上，先对当前预算和有界的大预算做一次小范围对照，分别测响应计算次数、父缓存淘汰、唯一描述子数、峰值显存和区域匹配耗时。预算是资源配置，不应改变匹配输出。

如果淘汰几乎消失且响应计算降到接近实际需要的唯一描述子数量，就能确认工作集问题得到解决；若总耗时仍高，则说明采样调度和主机循环占比已成为下一瓶颈。不要仅观察 allocated 升高就宣称优化成功。

### 第二优先：响应复用调度与 GPU 前筛

引入模板块优先调度，减少大缓存依赖；将当前 NumPy 分数／覆盖率筛选迁到设备端，只回传幸存中心。记录回传候选数、拷贝字节、kernel 数量和主机等待时间，验证低占用是否源于调度间隙。

### 第三优先：把筛选放到采样之前

使用模态、可评估权重上界、空间范围及描述子匹配上界，在不计算全部槽位响应时排除必然不合格的模板／中心。第 10 图仍有约 99.98% 比较进入密集回退，仅加速穷举并不能解决长期复杂度。

证明不了不会漏检的截断应明确标为“未检完／未知”，不能直接新建节点；保留学习歧义竞争者。候选早停条件必须足以保证最佳候选与所需分差，而不是找到一个可接受匹配就退出。

### 第四优先：GPU 图镜像与长期记忆增长治理

在前几项验证后再投入完整的 GPU 槽位／成员索引。与此同时，检查未被有效模板引用的 I 层节点、等价区域归并后的引用清理，以及实体提案的可重复性。

本次每张图仍新建 64 个实体、跨图更新为 0，稳定实体为 0；III 层到 512 后保持不变是候选预算的结果，不能当作模型已收敛。最终 512 个实体的原始命中与有效支持总量均为 512，提示保留下来的候选仍主要只有一次正证据。不同图片是否包含重复物体尚无真值，不能据此判定算法必然有错，但性能提升后仍须单独验证学习质量。

## 8. 边界

本报告没有实际调整缓存到 2 GiB、改写 GPU 图表示或执行新的性能实验。容量估算建立在当前 256×256、float32 和日志中的节点规模；后续全量 593 图学习可能达到完全不同的工作集。

结论是：**增加显存驻留和迁移数值匹配链路可行，且有明确的日志依据；短期最值得做的是解决缓存反复淘汰与把前筛留在 GPU，中长期必须减少密集搜索数量。** 不建议把当前重点转为全量搬迁 Python 图对象或升级硬件。
